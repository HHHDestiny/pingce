# 多 Agent 智能运维系统 — 按实际架构整理

> **前提澄清**：
> 1. 监控系统（夜莺 / Prometheus + AlertManager）是**已经存在的现成系统**，负责采集、存储、阈值判定和告警推送。本项目不做采集。
> 2. 告警治理与触达由**自己二开的运维平台**承担（基于开源项目二开，`<待填：具体开源项目名>`），负责精准分发、聚合降噪、限流、飞书卡片通知与恢复翻转。
> 3. 多 Agent 系统负责告警进来之后的分析与处置：二次确认、根因定位、自愈、审批。
>
> 状态：**POC / 灰度验证阶段**。

## 0. 实际架构与职责边界

```
┌──────────────────────────────────────────────────────────┐
│  已有监控系统（夜莺 / Prometheus + AlertManager）          │
│  采集 · 存储 · 阈值判定 · 告警推送                         │
└──────────────────────┬───────────────────────────────────┘
                       │  webhook POST（告警事件 JSON）
┌──────────────────────▼───────────────────────────────────┐
│  ① 告警接入 Agent（多 Agent 系统入口）                     │
│     标准化 → 指纹去重 → 时序二次确认 → 图谱富化             │
└──────────┬──────────────────────────────┬────────────────┘
           │ aiops.alerts                 │
┌──────────▼───────────────┐              │
│  ② AIOps Agent 链路       │              │
│    RCA 根因分析            │              │
│    Heal 故障自愈           │              │
│    Change 变更审批         │              │
└──────────┬───────────────┘              │
           │ 分析结果回流（根因/置信度/处置建议）│
           ▼                              ▼
┌──────────────────────────────────────────────────────────┐
│  ③ 二开运维平台层（告警治理 + 触达）                        │
│     聚合降噪 → 精准分发 → 全局限流 → 飞书卡片发送            │
│                      ▲                    │               │
│                      │  按钮回传（认领/屏蔽/恢复确认）       │
│                      └────────────────────┘               │
│     恢复检测 → 同一张卡片原地翻转（红 → 绿）→ 落库沉淀       │
└──────────────────────────────────────────────────────────┘
```

**职责边界（面试讲"边界感"的利器）：**

| 环节 | 谁负责 | 说明 |
|------|--------|------|
| 指标采集、存储 | 已有监控系统 | 不碰 |
| 阈值判定、告警产生 | 已有监控系统（多为静态阈值） | 不碰 |
| 告警接入、标准化 | 多 Agent 系统 | 兼容夜莺 / AlertManager 两种格式 |
| 告警量降噪（聚合/去重） | **二开运维平台** | 时间窗 + 拓扑聚类合并告警风暴 |
| 告警质降噪（抖动过滤） | 多 Agent 系统 | 三算法投票二次确认 |
| 精准分发 / 限流 / 通知 | **二开运维平台** | 服务 owner 映射 + 令牌桶 + 飞书卡片 |
| 根因定位 | 多 Agent 系统 | 知识图谱 + 贝叶斯 |
| 自愈执行 | 多 Agent 系统 | L0 自动执行，L1/L2 只出建议 |
| 恢复检测与状态翻转 | **二开运维平台** | 卡片原地更新，数据落库 |
| 风险评估与审批 | 多 Agent 系统 | 五因子评分 + 分级审批 |

**为什么这样切**：监控系统已经在用，推倒重来成本极高；它的问题是**误报多、定位慢**，不是"不能告警"。运维平台是公司内部工具链的既有入口，通知、值班、权限都在那里，告警治理放在这层最顺。多 Agent 系统则是纯粹的"智能层"，两边通过 webhook 和回调解耦，谁都不用改。

**一句话总结三层关系**：监控系统负责**发现问题**，多 Agent 负责**想清楚问题**，运维平台负责**找到对的人、说得清、收得了尾**。

## 1. 二开运维平台层：告警治理闭环

> 这一层基于开源运维平台二开（`python/alerting/` 下已有接入侧代码，平台侧为独立服务）。
> 四个能力：**聚合降噪 → 精准分发 → 全局限流 → 卡片翻转**。

### 1.1 聚合告警降噪

#### 为什么要单独做聚合

上游监控系统是按**规则**告警的，一条规则一个告警。一个 MySQL 主库抖动，会同时打爆 20 条规则 × 10 个服务 = 200 条告警，全推到群里就是灾难 —— 真正的信息（"主库出问题了"）被淹掉了。

聚合的目标：**把同一场故障的 200 条告警，压成 1 张卡片**。

#### 三层降噪的层次划分（面试重点，容易被问"你的降噪到底降的是什么"）

| 层次 | 降的是什么 | 手段 | 位置 |
|------|-----------|------|------|
| 量的降噪 | 告警风暴重复 | 时间窗聚合 + 指纹去重 + 拓扑聚类 | **运维平台层** |
| 质的降噪 | 单条告警是抖动还是真故障 | 三算法投票二次确认 | 多 Agent 接入层（见第 4 节） |
| 通知降噪 | 一个人被反复 @ | 按人降频 + 屏蔽期 | **运维平台层** |

这三层是没有重复劳动的：聚合解决"太多"，二次确认解决"太假"，降频解决"太吵"。

#### 聚合实现

**聚合键（group key）的优先级**：

```
1. 根因服务/拓扑簇      —— 最理想，告警按图谱聚类到同一个根因
2. rule_name + service  —— 同规则同服务
3. rule_name + 业务线   —— 同规则跨服务（如全站 5xx）
4. rule_name            —— 兜底
```

第 1 条是关键：如果 RCA 已经给出根因（置信度 ≥ 阈值），就用**根因服务**做聚合键，而不是用告警自己的服务 —— 这样"order-service 报超时、payment-service 报超时、api-gateway 报 5xx"会聚到同一个根因上，卡片标题直接写"疑似 mysql-primary 故障，影响 3 个服务"。这是 Agent 分析结果回流到平台的价值体现。

**窗口策略**：

```
滑动窗口 60s（可配），窗口内同键告警合并进同一个 AlertGroup
窗口到期 或 累计达 max_size(50) → 立即 flush，不等窗口结束
```

加 max_size 是防止窗口期内疯狂堆积导致通知延迟 —— 50 条已经足够说明"这是场风暴"，没必要等满 60 秒。

**合并时保留什么**：

| 字段 | 取值方式 |
|------|---------|
| 等级 | 窗口内**最高**等级（不能取平均，一条 P0 不能被 50 条 P2 稀释） |
| 故障起始时间 | 窗口内**最早**的触发时间（MTTR 计时起点） |
| 影响面 | 服务列表去重 + 图谱算受影响服务数 |
| 告警计数 | 累计条数，展示为"共 47 条告警" |
| 样例 | 保留前 3 条详情，其余折叠 |

**后续同类告警不新建卡片**：窗口关闭后如果还有同键告警进来，不新发消息，而是**更新已发卡片的计数**（复用 message_id）。这一点和 1.4 的卡片翻转是同一套机制 —— 卡片从"共 47 条"变成"共 63 条"，群里不新增任何消息。

#### 这个数字怎么算

可测指标：**告警压缩率 = 1 - 实际发送卡片数 / 原始告警条数**。

统计方法：在平台侧埋点记录每个窗口的 (原始告警数, 实际发送卡片数)，故障复盘时按场次汇总。这个数字**必须实测**，不能拍 —— 而且它依赖于聚合键选得好不好，聚合键选错压缩率立刻掉下来，面试官追问"为什么只有 60%"时你能讲出调优过程。

### 1.2 精准分发

#### 路由表设计

按你确认的方案：**服务 / 业务线 owner 映射**为主。

```yaml
service_owners:
  order-service:     {team: 交易, owner: 张三, open_id: ou_a1, chat_id: oc_trade}
  payment-service:   {team: 支付, owner: 李四, open_id: ou_b2, chat_id: oc_pay}
  inventory-service: {team: 供应链, owner: 王五, open_id: ou_c3, chat_id: oc_sc}
  mysql-primary:     {team: DBA,  owner: 赵六, open_id: ou_d4, chat_id: oc_dba}

business_line_fallback:      # 服务未命中时按业务线兜底
  交易:   {chat_id: oc_trade}
  支付:   {chat_id: oc_pay}

default:                     # 最终兜底
  {chat_id: oc_oncall, escalate_to: TL}
```

**匹配顺序**（从精确到宽泛，短路返回）：

```
① 精确服务名        order-service          → 张三 + 交易群
② 服务名模式匹配    order-* / *-service    → 交易群
③ 标签 team/env      tags.team=trade       → 交易群
④ 业务线兜底        → 对应业务群
⑤ 全局兜底          → 值班群 + 标记未归属（用于反哺路由表补全）
```

第 ⑤ 步的"标记未归属"很重要：**每次兜底都是路由表的一个洞**，平台应该把这些未命中服务记下来定期补。这是把分发准确率持续做上去的机制，面试讲出来很加分。

#### 分发的三个维度

| 维度 | 内容 | 说明 |
|------|------|------|
| **群** | chat_id | 主通知渠道，团队可见 |
| **人** | @ open_id | 直接 @ owner，责任到人 |
| **升级链** | P0 未认领 5min → @TL → 电话 | 只认领了才算响应 |

升级链依赖 1.4 的按钮回传：**只有点了"认领"才算人已经接手**，否则到点自动升级。没有回传机制，升级只能靠"发了就算响应"，那是假响应。

#### 数据来源

| 数据 | 来源 | 现状 | 生产做法 |
|------|------|------|---------|
| 服务 → 团队 | CMDB / 服务树 | 配置硬编码 | 定时拉取 + 本地缓存（TTL 5min） |
| 团队 → 人 | 内部 HR / 组织架构系统 | 配置硬编码 | 同上 |
| oncall 值班人 | 值班表系统 | — | 按时间查当前值班人 |
| 飞书 open_id / chat_id | 飞书通讯录 API | 配置硬编码 | 用户授权后拿，或按手机号换 open_id |

**缓存 + 兜底快照**是必须的：CMDB 挂了不能导致告警发不出去，所以本地要有一份上次成功拉取的快照，CMDB 不可用时用快照并打告警。

#### 这个数字怎么算

可测指标：**分发命中率 = 匹配到明确 owner 的告警数 / 总告警数**。

统计方法：每次分发记一行日志 (service, 匹配层级, 是否命中 owner)，按周聚合。命中率低说明路由表有洞，正好驱动补全。这个数字同样要实测。

### 1.3 限流（全局发送配额）

#### 为什么需要

告警风暴时如果不限制发送速率：
1. 飞书侧会触发限流甚至临时封禁，导致**连 P0 都发不出去**
2. 群里刷屏，真正重要的消息被冲走
3. 通知通道成为整个故障响应链路的单点瓶颈

所以限流保护的是**通知通道本身**，这是稳定性设计，不是简单的"少发点"。

#### 三层配额

```
① 全局令牌桶（总配额）—— 保护飞书 API
   容量 B（突发容忍）+ 速率 R/s（持续速率）
   数值以飞书开放平台官方配额为准，做成配置项而非硬编码

② 按群配额 —— 防止单个群被刷屏
   同一 chat_id 60s 内最多 N 条，超出合并为汇总卡

③ 按人降频 —— 防止轰炸个人
   同一 open_id 5min 内最多 @ 1 次
```

#### 关键设计：限流不能吞掉 P0

这是限流最容易踩的坑 —— 风暴来了，令牌桶被 P2 占满，真正的 P0 反而被限掉。

解决：**配额分区（reserved quota）**，把全局桶切成优先级队列：

```
P0 预留 30% 配额（专用，P1/P2 抢不走）
P1 可用剩余 70% + P0 空闲时的溢出
P2 只能用剩余配额，超了直接丢弃（可以丢，P2 不紧急）
```

**超限处理策略（分级，不是一刀切）**：

| 优先级 | 超限处理 |
|--------|---------|
| P0 | 排队等待，永不丢弃（延迟最多 10s，超了转电话外呼） |
| P1 | 延迟重试（指数退避 1s/2s/4s），3 次后退化为合并汇总卡 |
| P2 | 直接丢弃，只累加计数到下一张汇总卡 |

**注意**：被限流丢弃的告警不是"消失"了 —— 计数会累计到后续卡片上（"另有 37 条 P2 告警未展示"）。**限流限的是通知，不是处理**，告警仍然进 AIOps 链路做分析和自愈。这个区分面试里一定要说清楚。

#### 这个数字怎么算

可测指标：**风暴期间实际发送条数 vs 原始告警条数**，以及**P0 发送成功率（应为 100%）**。

后者是最有价值的数字 —— "在我们的告警治理下，P0 告警的送达成功率是 100%，历史上没有因为限流丢过 P0"。这比"压缩率 99%"更打动人。

### 1.4 故障恢复与飞书卡片翻转

#### 卡片生命周期

```
firing（红）──认领──► acked（黄）──恢复──► resolved（绿）
     │                                        ▲
     └──────── 屏蔽（灰，静默期）──────────────┘
                                        └─ 也可人工点"恢复确认"
```

#### 翻转实现：更新同一条消息，而不是新发一条

故障卡片发出后记下返回的 `message_id`（飞书叫 `open_message_id`），恢复时用它把**同一条消息**的内容改掉：

```
发送：  POST  /open-apis/im/v1/messages?receive_id_type=chat_id
        body: {receive_id, msg_type: "interactive", content: "<卡片JSON字符串>"}
        resp: {message_id: "om_xxx"}   ← 存起来，这是翻转的钥匙

翻转：  PATCH /open-apis/im/v1/messages/{message_id}
        body: {msg_type: "interactive", content: "<新卡片JSON字符串>"}
```

**为什么翻转而不新发**：
1. 群里不刷屏 —— 故障 200 条告警已经压成 1 张卡，再发 1 张恢复卡就翻倍了
2. 故障和恢复天然成对 —— 同一条消息上，上下文完整
3. **MTTR 一屏可见** —— 卡片底部直接写"持续 4分32秒"，不用人去翻两条消息对时间

> 接口细节以飞书开放平台最新文档为准。另一个可选路径是卡片**回传更新**：按钮回调的响应里直接返回新卡片 JSON，飞书会用它覆盖原卡片（适合"点击即翻转"的场景，不需要调 API）。系统侧主动恢复用 PATCH，用户点击用回传返回，两条路都保留。

#### 翻转匹配：怎么找到该翻哪张卡

resolved 告警进来后，**必须能反查到 firing 卡片**：

```
fingerprint（规则名+服务+标签 的 MD5）→ message_id 映射
存储：Redis（生产）/ 内存（POC），带 TTL（如 24h）
```

映射表是这层的核心状态。恢复告警和故障告警的 fingerprint 必须一致 —— 如果上游在恢复时改了任何标签（比如把 `severity` 从 1 改成 0），指纹就对不上，卡片永远翻不了。**生产上要专门处理"指纹归一化"**：只把稳定字段（规则名、服务、实例）纳入指纹，等级和触发值这类会变的不进指纹。

#### 恢复的三种判定来源

| 来源 | 说明 | 优先级 |
|------|------|--------|
| 上游推 resolved 告警 | 监控系统恢复后主动推，最权威 | 主 |
| 连续 N 个周期指标正常 | 上游没推恢复时的兜底（如连续 3 个采集周期正常判定恢复） | 兜底 |
| 人工点"恢复确认" | 卡片按钮回传 | 补充 |

兜底那条很实际：很多监控系统配置了"恢复通知"开关，一旦关掉就永远收不到 resolved，卡片会一直红着。自研兜底判定能保证卡片状态最终一定会收敛。

#### 幂等与乱序（这是翻转最容易出 bug 的地方）

| 异常场景 | 处理 |
|---------|------|
| resolved 早于 firing 到达（网络乱序） | 暂存 resolved 事件，firing 卡发出后立即翻转 |
| 重复收到 resolved | 按 fingerprint 幂等，已是 resolved 直接忽略 |
| 已翻转后又收到 firing | 判定为**二次故障**：更新卡片为 firing 并重置计时，或开新卡（看策略，推荐开新卡保留故障史） |
| 屏蔽期内恢复 | 仍然翻转（静默的是通知，不是状态机） |
| PATCH 失败 | 重试 3 次，失败则记录"卡片状态不一致"告警，人工兜底 |

#### 按钮回传

卡片上挂 action 按钮，点击后飞书 POST 到平台配置的回调地址：

```
按钮：  认领  |  屏蔽 30min  |  恢复确认  |  查看详情

回调体（关键字段）：
  action.value      {"action": "ack", "incident_id": "..."}
  open_message_id   卡片标识（可直接用于翻转）
  user_id / open_id 点击人
  token             验签用
```

| 按钮 | 系统动作 | 价值 |
|------|---------|------|
| 认领 | 状态 firing → acked，卡片变黄，记录认领人 | **MTTA（平均响应时长）的数据源**；未认领才升级 |
| 屏蔽 30min | 写静默规则，窗口内同指纹不再发卡（但仍计数、仍处理） | 给处置留出安静窗口 |
| 恢复确认 | 人工标记恢复，触发翻转 | 上游没推 resolved 时的补充 |
| 查看详情 | 跳转平台详情页（根因、拓扑图、时序图） | 把人引到能决策的地方 |

**安全**：回调必须验签（飞书的 `token` / challenge 机制），否则任何人都能伪造请求把告警全屏蔽掉 —— 这是告警系统最危险的漏洞，等于给了攻击者一个"让运维变瞎"的开关。

#### 卡片上放什么

```
┌─────────────────────────────────────────┐
│ 🔴 P0  订单服务异常（共 47 条告警）        │  ← 色条 + 等级 + 聚合计数
├─────────────────────────────────────────┤
```

### 1.5 ⭐ 这一层解决了 MTTR 数字的来源问题

这是加这层最大的收益 —— 之前文档里"MTTR 40min → 5min"是无源之水，现在**有了明确的采集点**：

每次卡片翻转，把这条记录落库：

```
(fingerprint, 首次触发时间, 认领时间, 恢复时间, 根因, 处置方式, 认领人, 告警条数)
```

于是三个核心指标全部可算，且**不再依赖人工填报**：

| 指标 | 算法 | 数据来源 |
|------|------|---------|
| **MTTA** 平均响应时长 | 认领时间 − 首次触发时间 | 按钮回传 |
| **MTTR** 平均恢复时长 | 恢复时间 − 首次触发时间 | 卡片翻转落库 |
| **自愈贡献率** | 自动恢复次数 / 总恢复次数 | 恢复方式字段 |

**这才是简历上"MTTR 从 40min 降至 5min"该有的出处**：40min 是治理前靠人工填报/工单时间统计的基线，5min 是治理后从卡片落库数据里算出来的。两者口径不同要说明，但它是**可复现、可追问**的。

面试被追问"这个 5 分钟怎么统计的"，标准回答：

> "故障卡片发出时记首次触发时间，恢复翻转时记恢复时间，每次翻转落一条库记录，MTTR 就是这两个时间的差值取平均。响应时间靠卡片上的认领按钮回传。治理前的 40 分钟是从工单系统里捞的人工填报数据，口径不完全一致，所以我在简历上写的是'灰度期间'。"

## 3. 知识图谱 + BFS + 贝叶斯根因定位

拓扑数据 `knowledge_graph.py:287-342`：**11 个服务节点 + 15 条 DEPENDS_ON**。

```
api-gateway → order-service, user-service, inventory-service
order-service → payment-service, inventory-service, user-service, kafka-broker
payment-service → mysql-primary, redis-cache
inventory-service → mysql-primary, elasticsearch
user-service → mysql-replica, redis-cache
notification-service → kafka-broker
mysql-replica → mysql-primary
```

**推理过程**：告警服务 → 反向 BFS 展开依赖链 → 收集证据（指标异常 0.8 / 近期变更 0.9 / 严重度 0.5）→ 贝叶斯打分。

```
P(根因|证据) = P(证据|根因) × P(根因) ÷ 0.5
```

| 候选根因 | 先验 | 似然 | 后验 |
|---------|------|------|------|
| 请求量激增致 CPU 过载 | 0.35 | 0.6 | 0.42 |
| 内存泄漏致 GC 频繁 | 0.25 | 0.6 | 0.30 |
| **近期代码部署性能退化** | 0.30 | **0.9**（命中变更证据） | **0.54** ✅ |
| 下游响应慢耗尽线程池 | 0.10 | 0.5 | 0.10 |

超过 0.3 门控 → 放行自愈 → 匹配 rollback 剧本 → 完整闭环。

⚠️ 两个已知实现问题：RCA 用的是硬编码拓扑（`rca_agent.py:35`），没接知识图谱；`_trace_dependency_chain()` 注释写 BFS 实为递归 DFS（`rca_agent.py:194`）。

## 4. 三算法检测 —— 实际用在哪、怎么实现

### 4.1 关键澄清

**不是采集端检测，是告警进来后的二次确认。**

上游监控系统用静态阈值（CPU > 80%），业务波动期误报很多。本系统在告警到达后：

1. 用告警里的 PromQL / 指标名，**反查监控系统**拿告警时刻前 30 分钟的时序
2. 对这段时序跑 3-Sigma / EWMA / Isolation Forest 投票
3. 投票通过 → 确认真异常，放行到 RCA；不通过 → 判定抖动，直接抑制

### 4.2 数据从哪来

`MetricFetcher.fetch_series()`（`alerting/alert_ingest.py`）：

```python
GET {prometheus_url}/api/v1/query_range
    ?query=cpu_usage_percent{service="order-service"}
    &start={告警时刻 - 1800}&end={告警时刻}&step=30s
```

取返回的 `result[0].values`，转成 float 列表作为历史基线，**当前点用告警的 trigger_value**。

工程细节（面试能讲）：
- **窗口选 30 分钟 / step 30s** → 60 个点，兼顾及时性和样本量
- **mock 模式**：本地没有 Prometheus 时用合成数据（趋势+周期+噪声），链路照样能跑通
- **拉取失败降级**：拿不到时序就不做二次确认，直接采信上游判定，不会因为查不到数据把告警丢了

### 4.3 三种决策分支

| 分支 | 触发条件 | 动作 |
|------|---------|------|
| `confirmed_by_vote` | 三算法 ≥2 票命中 | 放行，进 RCA |
| `confirmed_by_upstream` | 历史样本 < 10 点，或投票没过但上游判 CRITICAL | 放行（宁可多查一次，不可漏 P0） |
| `suppressed` | 投票未通过且非 CRITICAL | 抑制，不进后续流程 |

CRITICAL 兜底这条很重要：**算法可以保守，但 P0 不能靠算法赌**。

### 4.4 实测数据（简历数字的真实来源）

评测脚本 `python/benchmarks/anomaly_eval.py`，600 个点，注入 18 个标注异常：

| 策略 | TP | FP | FN | 精确率 | 召回率 | 误报率 | F1 |
|------|----|----|----|--------|--------|--------|-----|
| 静态阈值 (>80) | 8 | 59 | 10 | **11.94%** | 44.44% | **11.09%** | 0.188 |
| 单算法 3-Sigma | 6 | 0 | 12 | 100% | 33.33% | 0% | 0.500 |
| 单算法 EWMA | 17 | 2 | 1 | 89.47% | 94.44% | 0.38% | 0.919 |
| **三算法投票 (≥2)** | **17** | **0** | **1** | **100%** | **94.44%** | **0%** | **0.971** |
| 投票·全量历史基线 | 14 | 0 | 4 | 100% | 77.78% | 0% | 0.875 |

**结论：**

- 静态阈值在这份数据上 **59 次误报、精确率仅 11.9%** —— 数据有趋势和周期，后半段基线自然冲上 80，正常波动全被当成异常
- 三算法投票 **精确率 100%、召回 94.4%、误报率 0%、F1 0.971**
- 三个算法互补性被验证：单 3-Sigma 召回只有 33%（趋势撑大了 σ），单 EWMA 有 2 次误报，**投票后两者缺点互相抵消**
- 基线窗口用滚动 120 点（F1 0.971）明显优于全量历史（F1 0.875）

> 之前有一版结果说"投票召回只有 33%"，是因为当时 scikit-learn 没装上、Isolation Forest 弃权退化成双算法投票。**以本次完整三算法的结果为准。**

## 5. 分级自愈（低风险自动，高风险出建议）

### 5.1 三级策略

| 级别 | 动作 | 爆炸半径 | 处理方式 |
|------|------|---------|---------|
| **L0** | 重启 Pod、扩容、限流、熔断 | 0.01~0.08 | **自动执行** |
| **L1** | 回滚版本、回滚配置 | 0.10~0.15 | **出建议 + oncall 确认** |
| **L2** | 堆转储、数据库操作 | — | **出建议 + TL 审批** |

动作选择按风险从低到高优先匹配（`heal_agent.py:226-235`）：
`rate_limit → circuit_breaker → scale_up → restart_pod → rollback_config → rollback → heap_dump`

设计原则：**优先选代价最小的可执行项，而不是最"对"的那项** —— 自愈系统的第一原则是别把故障搞大。

### 5.2 四道护栏

```
① 熔断器（连续失败 5 次 → 熔断 60s，拒绝一切自愈）
② 动作匹配（无 Playbook 直接放弃，不盲动）
③ 爆炸半径（> 0.2 自动升级 L2）
④ dry-run（先渲染完整命令做合法性校验）
⑤ 风险审批（ChangeAgent 五因子评分 + 分级审批）
```

### 5.3 风险评分（五因子加权）

```
risk = 0.30×爆炸半径 + 0.25×操作类型 + 0.20×时间窗口
     + 0.15×历史失败率 + 0.10×服务关键度
```

手算 Demo 场景（order-service 执行 rollback）：

```
0.30×0.15 = 0.045   爆炸半径
0.25×0.60 = 0.150   rollback 操作风险
0.20×0.10 = 0.020   工作时间（非工作时段为 0.3）
0.15×0.10 = 0.015   历史失败率
0.10×0.90 = 0.090   order-service 关键度
─────────────────
            0.320    → L1，由 oncall 审批（非工作时间 0.36）
```

> ⚠️ README 里写的 `risk=0.158` 与代码算出的 0.32 对不上，是早期参数版本残留，**别背那个数**。

L1/L2 目前只改状态，生产上应通过运维平台的**审批卡片**（飞书审批 / 工单）触达，审批结果回写到事件总线 —— 这正好复用 1.4 的卡片回传机制。

```
  卡片挂载认领/屏蔽按钮支持交互回传；翻转时落库沉淀故障记录，

● 基于 Neo4j 构建微服务拓扑知识图谱（11 个服务节点 + 15 条依赖），

  分析结果回流至告警卡片

● 在告警接入侧实现 3-Sigma / EWMA / Isolation Forest 三算法投票的二次确认机制，

● 设计三级处置策略：L0 低风险自动执行，L1/L2 高风险生成建议并走人工审批，
```

相比原版改了什么：
- 第一条从"我做监控告警"改成"在已有监控之上做增强层" —— **边界清晰，且不显得在重复造轮子**
- 新增第二、三条，把运维平台二开讲成**独立且完整的治理闭环**，而不是"发个飞书通知"
- 第三条把 MTTR 数字的出处交代清楚（卡片翻转落库），这是最容易被追问的点
- 原第三条明确了"二次确认"定位和实测口径
- 最后一条明确了"高风险只出建议"

> 六条偏多的话，可以把第二、三条合并成一条（分发/降噪/限流一张卡，卡片翻转另一条卡），或把根因那条和二次确认那条合并。建议保留**卡片翻转**这条 —— 它最有辨识度，别人简历上不会有。

## 9. 一分钟话术

> "我们公司已经有夜莺做监控告警，但它有两个问题：静态阈值误报多，告警进来后定位靠人翻面板。所以我在下游做了两层东西。
>
> 第一层是**多 Agent 智能层**，不侵入现有监控——夜莺把告警 webhook 推过来，接入层先做去重和三算法投票的二次确认，把抖动和周期波动挡掉；确认后的告警关联知识图谱做富化，带着拓扑位置和近期变更进根因分析，用反向 BFS 找传播链、贝叶斯给候选根因打分；然后按风险分级处置，低风险的重启、限流自动执行，高风险的回滚只出建议走人工审批。
>
> 第二层是**二开的运维平台**，负责告警治理和触达：一个故障会打爆几百条告警，我按时间窗和拓扑关系聚合成一张卡片；按服务 owner 映射精准分发到对应团队和负责人；全局令牌桶限流保护通知通道，P0 有预留配额不会被限掉。通知用飞书互动卡片，恢复的时候**同一张卡片原地翻转**，群里不刷屏，持续时间一屏可见，卡片上还挂了认领和屏蔽按钮支持回传。
>
> 这套设计有个额外收益：每次卡片翻转都会落一条库记录，故障的触发时间、认领时间、恢复时间、根因、处置方式全有了，MTTA 和 MTTR 不用再靠人工填报。灰度期间 MTTR 从 40 分钟降到 5 分钟，接入侧的降噪我用标注数据集实测过，精确率从 11.9% 提到 100%。"
